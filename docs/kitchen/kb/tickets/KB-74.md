# [TEMPO-KB-74] Mobile navigation drawer keeps keyboard focus in view

FOR: tempo-rhythm, Kitchen run KB, lane UI, code model WORKHORSE. One focused accessibility repair to the existing web shell.

WHEN: Start from integration after lead admission. On 19 Oct a query of **all 107 open PR file lists** found no active writer of `TempoShell.tsx`. PR #1081 writes `Sidebar.tsx` only, so this ticket does not edit it. Open held issue #858 proposes a distinct future workspace-navigation feature that also lists `TempoShell.tsx`; it must serialize or rebase after this narrow repair. This ticket does not implement #858 or create navigation destinations. KA-41 #1124 later writes `Sidebar.tsx` and depends on #1081; neither is a source dependency for a TempoShell-only focus repair.

WHY: In `TempoShell.tsx`, the Sidebar is earlier than Topbar/TabBar in DOM order. At <=1023 px, `tempo.css` makes it a fixed overlay when `data-rail=open`. The two menu callbacks only toggle `railOpen`; they do not move focus into the opened Sidebar. After opening from the topbar, the next forward Tab can enter the visually obscured page instead of the drawer. Escape/pathname dismissal only closes the drawer; focused content inside becomes inert with no deliberate return. This is a source-proven keyboard defect on the existing mounted shell, not a new feature request. See `docs/kitchen/kb/INVENTORY.md` lines 146–149 and DESIGN.md §§6, 8–10 and HARD_RULES.md §§1, 5–8, 11; Amit’s brief 19 Oct asks for complete component polish alongside search/history improvements.

GOAL: At phone/tablet width, the real Sidebar opens as a usable modal navigation drawer. Keyboard focus enters it, stays in it until dismissal/navigation, and lands in a sensible visible place after it closes. Desktop rail and the existing coach/command overlays keep their behavior.
